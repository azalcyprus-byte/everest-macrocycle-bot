# Everest Macrocycle Bot

Закрытый Telegram-бот для системы Macrocycle #3.

## Команды

- `/start` — проверка бота и авторизации.
- `/sheet` — проверка Google Sheets.
- `/readtest` — чтение рабочих данных.
- `/writetest` — безопасный тест записи в план-факт.
- `/calendartest` — чтение календаря и поиск пересечений.
- `/eventtest` — создание, изменение и удаление тестового события.
- `/schedulertest ЧЧ:ММ` — устойчивое плановое задание.
- `/schedulerstatus` — статусы планировщика.
- `/journaltest` — журналирование действия и блокировка повторного исполнения.
- `/journalstatus` — последние записи журнала.
- `/dayplantest` — основной тест: прочитать план дня и три утренних чек-листа, определить допуск онлайн-сессии и отправить отдельное сообщение координатора.
- `/dayplantest repeat` — повторный прогон в тот же день с отдельными тестовыми ID.
- `/fullplantest` — собрать полный план дня: игра, работа над игрой, приёмы пищи и допущенные задачи.
- `/fullplantest repeat` — повторный прогон полного плана.
- `/hqtest` — сквозной тест координатора: обычный итоговый план дня без технической обвязки.
- `/hq <поручение>` — передать поручение координатору.
- `/hqstatus` — статус manager-agent, утреннего оркестратора и подключённых модулей.
- `/morningstatus` — статус сегодняшней утренней сессии и трёх чек-листов.
- `/morningcheck` — немедленно проверить новые ответы форм и обновить статус.
- Обычный текст без команды обрабатывается координатором. Любое сообщение, содержащее `Доброе утро`, запускает или продолжает утреннюю сессию.
- `/dayplancleanup CONFIRM` — удалить тестовые записи `/dayplantest` и `/fullplantest` из планировщика и журнала действий.
- `/notifytest ЧЧ:ММ` — старый тест уведомления в памяти процесса.
- `/buttonstest` — тестовая карточка с кнопками.

## Блок №25: журнал действий и идемпотентность

При первом вызове бот создаёт вкладку `16_Журнал_действий`.

Каждое действие, выполняемое через обязательный исполнитель
`execute_action_once`, получает:

- уникальный `ACTION_ID`;
- `IDEMPOTENCY_KEY`;
- операцию, тип и ID объекта;
- источник и цель;
- хеш и JSON входных данных;
- статус `STARTED`, `SUCCEEDED` или `FAILED`;
- JSON результата;
- время начала и завершения;
- количество заблокированных дублей;
- ошибку, исполнителя и системную проверку.

### Механизм защиты

1. До побочного эффекта создаётся строка со статусом `STARTED`.
2. Ключ идемпотентности проверяется под межпоточным lock.
3. Если ключ уже существует, действие не выполняется.
4. В существующей строке увеличивается счётчик дублей.
5. После успеха строка переводится в `SUCCEEDED`.
6. После ошибки — в `FAILED`.
7. Состояние `STARTED` также блокирует повтор, что безопаснее
   повторного исполнения при неопределённом результате.

### Тест `/journaltest`

Команда:

1. регистрирует техническую запись до исполнения;
2. один раз записывает маркер в `10_План_факт_дня!R503`;
3. читает маркер и проверяет формулы;
4. очищает ячейку;
5. повторяет тот же запрос с тем же ключом;
6. проверяет, что повтор заблокирован, а действие выполнилось ровно один раз;
7. оставляет одну итоговую строку журнала как доказательство теста.

Рабочие показатели дня не изменяются.

- `COORDINATOR_OPENAI_TIMEOUT_SECONDS` — таймаут маршрутизации; по умолчанию `30`.
- `MORNING_FORM_URL` — ссылка для кнопки первого чек-листа `Утро`.
- `MORNING_60_FORM_URL` — ссылка для кнопки второго чек-листа `Утро 60 мин`.
- `MORNING_90_FORM_URL` — ссылка для кнопки третьего чек-листа `Утро 90 мин`.
- `MORNING_SECOND_DELAY_MINUTES` — задержка второго чек-листа; по умолчанию `60`.
- `MORNING_THIRD_DELAY_MINUTES` — задержка третьего чек-листа; по умолчанию `90`.
- `MORNING_REMINDER_INTERVAL_MINUTES` — повтор напоминаний о незаполненной форме; по умолчанию `15`.
- `MORNING_READY_DELAY_MINUTES` — задержка сообщения о готовности после последней формы; по умолчанию `5`.
- `MORNING_ORCHESTRATOR_TICK_SECONDS` — частота технической проверки форм; по умолчанию `60`.

## Обновление v11.0: тест утреннего планирования

Команда `/dayplantest` использует текущую дату по Москве и читает:

- `Утро`;
- `Утро 60 мин`;
- `Утро 90 мин`;
- план игры и study из `02_День`.

Бот проверяет наличие всех трёх чек-листов и оценивает:

- ясность мышления;
- восприятие информации;
- устойчивость внимания;
- остаточную перегрузку и раздражение;
- физическое восстановление;
- сонливость;
- запас энергии;
- качество сна `0–10` из `02_День`. Этот показатель уже учитывает продолжительность сна, скорость засыпания, ночные пробуждения, помехи и температуру.

Правило качества сна по умолчанию:

- `1,0–3,0` — `RED`, сегодня лучше не играть;
- `3,1–5,4` — `YELLOW`, сессия сокращается;
- `5,5–10,0` — качество сна само по себе не ограничивает игру.

Результат:

- `GREEN` — сессия разрешена полностью;
- `YELLOW` — сессия сокращается до двух третей планового объёма с округлением до 30 минут;
- `RED` — штаб рекомендует не играть;
- `INCOMPLETE` — решение не принимается, пока не найдены все данные;
- `NO_GAME` — по плану онлайн-игры нет.

Тестовое сообщение сохраняется во вкладке `15_Планировщик`, действие фиксируется во вкладке `16_Журнал_действий`, после чего сообщение доставляется отдельным Telegram-сообщением. Основной прогон за дату защищён от повторного запуска.

Это обновление не формирует меню, не назначает число столов и не создаёт полный план дня: эти параметры не выдумываются до утверждения соответствующих правил.


## Обновление v11.1: качество сна

`/dayplantest` теперь обязательно читает `Качество сна, 0-10` из строки текущего дня на вкладке `02_День`. ## Обновление v11.2: полный план дня

Команда `/fullplantest` использует уже принятое решение по игровой сессии и формирует конкретное расписание.

Источники:

- план игры, работы над игрой, фаза и тип дня — `02_День`;
- времена приёмов пищи — последний существующий шаблон того же типа дня в `10_План_факт_дня`;
- уже назначенные на сегодня блоки — `10_План_факт_дня`;
- дополнительные задачи — `05_Проекты_и_задачи`.

Дополнительная задача включается только если:

- статус задачи активный;
- `Статус допуска = Готово`;
- нет блокера;
- тип дня и фаза входят в допустимые;
- задача помещается в свободное окно до `FULL_PLAN_DAY_END`.

Правила распределения:

- онлайн-игра начинается в `ONLINE_GAME_START`;
- при `YELLOW` используется сокращённая продолжительность из решения штаба;
- после игры ставится окно восстановления `STUDY_AFTER_GAME_GAP_MINUTES`;
- работа над игрой сохраняет плановый объём;
- приём пищи не ставится внутрь непрерывного учебного блока: блок автоматически разделяется на две части;
- при `RED` онлайн-игра и работа над игрой в тестовом плане не назначаются;
- неподтверждённые задачи бот не вставляет самовольно.

Команда не записывает рабочий план в `10_План_факт_дня` и не меняет Google Calendar. Она только формирует тестовое Telegram-сообщение через устойчивый планировщик.


## Обновление v12.1: координатор как manager-agent — блок №26

Координатор перестал быть простым echo-обработчиком. Обычные Telegram-сообщения и команда `/hq` проходят единый контур:

1. классификация запроса;
2. определение класса действия;
3. выбор минимального набора подключённых модулей;
4. чтение нужных источников;
5. сборка одного сводного ответа;
6. журналирование обработки с ключом идемпотентности.

Поддерживаемые ветки первой версии:

- `BUILD_DAY_PLAN` — полный план дня из текущего состояния, игры, study, питания и допущенных задач;
- `SESSION_STATUS` — решение по игровой сессии с учётом качества сна и чек-листов;
- `MEAL_QUERY` — время конкретного приёма пищи; меню не выдумывается до блока №28;
- `SYSTEM_STATUS` — состояние координатора и подключённых модулей;
- `REGISTER_REQUEST` — безопасная остановка неподдержанной категории без ложного исполнения.

Для известных команд используется строгая маршрутизация по правилам. Если заданы `OPENAI_API_KEY` и `OPENAI_MODEL`, неоднозначные обычные поручения дополнительно классифицируются через OpenAI Responses API. Модель не выполняет операции сама: фактические чтения и решения остаются в проверяемом коде и в пределах утверждённых полномочий.

### Проверка блока №26

1. Загрузить `bot.py` и перезапустить Railway.
2. Отправить `/hqstatus`.
3. Отправить `/hqtest`.
4. Отправить обычным текстом: `Составь план на день`.
5. Отправить: `Можно сегодня играть?`.
6. Отправить: `Что у нас на второй завтрак?`.

Блок считается завершённым только после успешной проверки этих веток в реальном Telegram. До этого дорожная карта должна сохранять статус `В работе`.

## Учёт текущего времени в координаторе

Версия v12.1 не выдаёт прошедший утренний план как актуальное расписание.

- обычный запрос «Составь план на день» показывает только текущие и будущие блоки;
- активный блок помечается как «Сейчас–HH:MM»;
- завершившееся игровое окно описывается как прошедшее утреннее решение;
- прошедшие блоки не считаются выполненными без подтверждённого FACT;
- запрос «Покажи полный план на день» выводит всю хронологию, но сохраняет актуальный статус игрового окна.


## Обновление v12.2.1: восстановленный утренний оркестратор

Утренний сценарий снова является частью рабочего кода.

1. Любое сообщение с фразой `Доброе утро` создаёт одну утреннюю сессию на текущую московскую дату.
2. Бот приветствует Андрея Николаевича, добавляет меняющееся пожелание чемпионского дня и показывает кнопку первого чек-листа.
3. Второй чек-лист становится актуальным через 60 минут от запуска сессии.
4. Третий чек-лист становится актуальным через 90 минут.
5. Незакрытый чек-лист напоминается каждые 15 минут. Каждая доставка имеет отдельный ключ идемпотентности и не дублируется при минутных проверках или перезапуске процесса.
6. Заполнение определяется по фактическим строкам текущей даты во вкладках `Утро`, `Утро 60 мин`, `Утро 90 мин`.
7. Через 5 минут после самой поздней из трёх записей бот один раз сообщает: `Мы готовы обсудить план на день.`
8. Повторное `Доброе утро` в тот же день не создаёт новую сессию и возвращает текущий статус с нужной кнопкой.
9. Сообщение `Буду готов через X минут/часов` фиксируется без запуска новых навязчивых напоминаний.
10. Состояние сессии и все отправки фиксируются во вкладке `16_Журнал_действий`; после Restart оркестратор продолжает работу по сохранённой сессии.

### Ссылки Google Forms

Реальные responder-ссылки трёх форм получены 30.07.2026 и подготовлены в файле `RAILWAY_MORNING_ENV.ready.txt`. Они по-прежнему не зашиты в `bot.py`: Railway остаётся источником конфигурации. `/hqstatus` показывает, сколько ссылок настроено. Значение, случайно переданное с окончанием `/formResponse`, автоматически преобразуется в безопасное `/viewform`.

### Проверка после развёртывания

1. `/hqstatus` должен показать версию `v12.2.1` и `формы настроены 3/3`.
2. Отправить `Доброе утро`.
3. Проверить приветствие и кнопку первого чек-листа.
4. Повторно отправить `Доброе утро`: новая сессия не должна создаться.
5. `/morningstatus` должен показать статусы `1/2/3`.
6. После отправки формы выполнить `/morningcheck` или дождаться автоматической проверки.
7. Полный блок №26 закрывается только после реального прохождения всей цепочки до сообщения о готовности плана.

## v12.3 — ускоренный сквозной тест утреннего сценария

После развёртывания выполните команду:

```text
/morningtest
```

Тест длится около 30 секунд при стандартном `MORNING_TEST_STEP_SECONDS=5` и не изменяет реальные ответы Google Forms или рабочую утреннюю сессию. Бот последовательно отправляет:

1. кнопку первой формы;
2. тестовое напоминание по первой форме;
3. кнопку второй формы;
4. тестовое напоминание по второй форме;
5. кнопку третьей формы;
6. тестовое напоминание по третьей форме;
7. итоговый результат с ACTION_ID.

Дополнительные команды:

```text
/morningtest status
/morningtest cancel
```

Итог считается техническим PASS, если пришли все семь сообщений, каждая кнопка открывает правильную форму, а финальный отчёт содержит зелёную отметку и ACTION_ID. Реальный утренний прогон по фразе «Доброе утро» остаётся финальной эксплуатационной проверкой.
