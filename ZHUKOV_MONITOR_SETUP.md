# Everest — мониторинг состояния Алексея Жукова

**Статус:** модуль включается отдельно; до настройки ZHUKOV_MONITOR_ENABLED=true уведомления не отправляются.

## Действующая архитектура

- Google Forms остаются прежними: ответы на вкладках «Утро — ответы» и «После игры — ответы».
- Google Apps Script (файл apps_script/ZhukovEvents.gs) записывает факт новой отправки в «Everest_Алексей_события».
- Существующий Everest Telegram-бот каждые 5 минут проверяет Sheets и формирует события.
- Отдельная вкладка «Everest_Алексей_мониторинг» хранит активацию, пропуски, аналитику, статус доставки и подтверждённые решения куратора.
- Анализ и уведомления отправляются только в чат куратора. Личные чек-листы куратора и напоминания Алексею не изменяются.

## Перед первым включением

1. Сервисному аккаунту из GOOGLE_SERVICE_ACCOUNT_JSON нужны права **Редактор** на таблицу Алексея. Старых прав «Читатель» для создания журнала недостаточно.
2. В таблице открыть Extensions → Apps Script. В существующем файле ZhukovEvents.gs использовать актуальный код apps_script/ZhukovEvents.gs. Если installAlexeyFormTrigger уже выполнялась, повторно запускать её не требуется. Выполнить вручную testAlexeyEventJournal: она проверяет триггер, временно пишет __TEST_ONLY__ в «Everest_Алексей_события», проверяет запись и удаляет только собственную строку. **Не заполнять форму Алексея тестовыми данными** — это исказит его статистику. Срабатывание настоящего триггера следует подтвердить после следующего реального ответа Алексея.
3. Уточнить Telegram ID приватного чата куратора; он не должен совпадать с ID Алексея.
4. **Город или часовой пояс Алексея для мониторинга не требуется.** Используется «Отметка времени» в часовом поясе Google Таблицы (Asia/Shanghai) и поле «Дата» для дня отчёта. Первая утренняя анкета после даты активации автоматически задаст опорную точку; архивные анкеты не участвуют. Необязательный ZHUKOV_MONITOR_ANCHOR_LOCAL трактуется как время именно Google Таблицы.
5. Проверить настройки Railway и включить мониторинг только после теста.

## Railway environment

Существующие переменные не удалять. Новые переменные:

    ZHUKOV_MONITOR_ENABLED=false
    ZHUKOV_CURATOR_CHAT_ID=<ID чата куратора>
    ZHUKOV_SHEET_TIMEZONE=Asia/Shanghai
    # ZHUKOV_TIMEZONE НЕ используется модулем мониторинга (но может использоваться старым контуром напоминаний Алексею)
    ZHUKOV_MONITOR_ANCHOR_LOCAL=<YYYY-MM-DDTHH:MM:SS первого опорного отчёта>
    ZHUKOV_MONITOR_EVENT_MODE=script
    ZHUKOV_MACROCYCLE_START_DATE=<YYYY-MM-DD, если известно>
    ZHUKOV_MACROCYCLE_PHASE=<текущая фаза, если известно>
    ZHUKOV_PRIORITY_TOURNAMENTS=<приоритетные турниры, если известны>
    ZHUKOV_MONITOR_OPENAI_ENABLED=false
    ZHUKOV_MONITOR_OPENAI_MODEL=gpt-4.1-mini

В режиме EVENT_MODE=script новые аналитические сводки инициируются событиями Apps Script. При отсутствии триггера временно использовать EVENT_MODE=poll для чтения непосредственно ответов; контроль пропусков работает в обоих режимах.

Опционально OPENAI_API_KEY и ZHUKOV_MONITOR_OPENAI_ENABLED=true включают дополнительную AI-гипотезу. По умолчанию сведения Алексея во внешнюю модель не отправляются. При отключении/сбое OpenAI контроль пропусков и базовая аналитика работают.

## Контроль времени и защита от дублей

Первый отчёт 01.10 в 08:00 **по времени Google Таблицы** → проверка отчёта за 02.10 в 14:00 02.10, за 03.10 — в 14:00 03.10, далее строго каждые **24 прошедших часа**. День отчёта определяется полем «Дата», даже если срок проверки приходится на другую календарную дату. Перелёты Алексея не смещают график, и его город не нужно сообщать куратору. При переходах на летнее/зимнее время отсчитываются именно прошедшие часы от единой опорной отметки.

Фактическая отправка может быть позднее контрольной минуты на срок до ~5 минут из-за периодического запуска бота.

Мониторинг при первом включении фиксирует дату активации и не рассылает исторические пропуски. Каждому пропуску соответствует один постоянный ключ, записываемый до Telegram-отправки. Неопределённая ошибка доставки помечается REVIEW, без автоматической повторной отправки, во избежание дублей. Рассчитано на один работающий экземпляр бота.

## Сводка

ФАКТ → НАБЛЮДЕНИЕ → ГИПОТЕЗА → ПРЕДЛАГАЕМОЕ РЕШЕНИЕ.

Данные за 3 дня, 7 дней и с начала макроцикла (если известна дата начала), иначе за всю имеющуюся историю. Оцениваются сонливость, окно сна (не измеренная продолжительность фактического сна), внимание, замедление простых решений, часы игры, конкретные сбои и автоматизм, изменение внимания и анализа между первой и последней третями сессии, пары «длинная игра → следующее утро» и «отдых → следующее утро». Нет рейтинга 0–100. Сон более 8 часов сам по себе не снижает нагрузку. Гипотезы не считаются доказанными причинами.

Решение куратора добавляется в историю отдельной строкой командой, доступной только владельцу:

    /zhukovdecision 2026-10-20 Оставить согласованный план и проверять внимание на перерывах

## 📅 План нагрузки и игровой день в заголовке

В новом ежедневном отчёте Everest (автоматическая сводка, `/zhukovai`, ретроспективный `/zhukovreport`) сразу под датой выводятся два **независимых** показателя:

- `📅 План нагрузки: O / L / L+ / M / T` — точный код из вкладки **«Волна по дням»** отдельной таблицы «Everest — Алексей Жуков». Поиск строго по дате, без подстановки соседнего дня.
- `🎮 Игровой день: Да (заявлено утром) / Нет (перелёт или отдых) / не указан` — ответ **«Сегодня»** в настоящем утреннем чек-листе Алексея в таблице «Everest — наблюдение за нагрузкой». Это план/декларация утром, а не подтверждение фактической игры; фактическую игру устанавливает постигровой отчёт.

Например, 20.10.2026: `📅 План нагрузки: O` и `🎮 Игровой день: Нет (перелёт)`. При отсутствии планового дня или однозначного ответа соответствующее поле показывает `не указан`, а не придуманное значение.

Источник плановых кодов доступен боту на правах **reader**: сервисный аккаунт `everest-macrocycle-bot@everest-macrocycle-bot.iam.gserviceaccount.com`. План и исходные формы не изменяются. Чтение плана кэшируется на 10 минут; при ошибке доступа обычная аналитика и предупреждения о пропусках продолжают работать.

Конфигурация: `ZHUKOV_PLAN_SPREADSHEET_ID` (по умолчанию ID таблицы «Everest — Алексей Жуков») и `ZHUKOV_PLAN_YEAR=2026`. Во вкладке «Волна по дням» используются даты без года (например, `20.10`), поэтому год зафиксирован отдельно. **При начале следующего планового года необходимо обновить `ZHUKOV_PLAN_YEAR` и период самого плана**, иначе год не угадывается. Для уже сохранённых исторических сообщений содержимое не меняется.

## 🏔️ Компактная ежедневная сводка для куратора

Для нового автоматического анализа после настоящей утренней анкеты, ручной команды `/zhukovai ДД.ММ.ГГГГ` и ретроспективной реконструкции `/zhukovreport` используется единый короткий отчёт, обычно одно Telegram-сообщение. Ранее **сохранённые** сводки остаются в оригинальном виде.

- **🏔️ Everest | Алексей Жуков | дата** — заголовок.
- **📅 План нагрузки** и **🎮 Игровой день** — две строки непосредственно после даты, с раздельными источниками.
- **✅ / 🟡 / 🟠** — вывод по нагрузке без оценки готовности в процентах.
- **🔎 Значимые изменения** — сдвиги или нехватка данных; без пересказа полей анкеты.
- **💡 Гипотеза** — максимум одна проверяемая версия; если оснований нет, это указано.
- **🎯 Рекомендация куратору** — одно действие, без автоматического уменьшения нагрузки.
- **ℹ️ Надёжность** — кратко о доступности данных за 7 дней.
- **💳 OpenAI API: ≈ $...** — в конце, только после успешного AI-вызова.

Python оценивает значимые сигналы, OpenAI получает обезличенные показатели и формулирует интерпретацию. Подробные технические метрики в ежедневное сообщение не включаются. Если OpenAI недоступен, бот присылает такую же компактную сводку с явной пометкой об отсутствии AI и без платёжной строки. Расписание пропусков и источник Google Форм не изменяются.

## 🤖 Дополнительная индивидуальная аналитика через OpenAI API

Модуль подготовки AI-гипотез реализован, но **не включается без секретного ключа и отдельного решения о передаче обезличенных данных ученика**. При включении модель заменяет шаблонные разделы «Гипотеза» и «Предлагаемое решение» в новых утренних отчётах на одну короткую проверяемую гипотезу и одно действие, если они обоснованны. Краткие выводы и достаточность данных контролирует Python. Если API не работает, остаётся детерминированная сводка. Пропущенные отчёты и все напоминания работают без API.

**Что передаётся:** ограниченные числовые и категориальные признаки за последние 14 дней, а также агрегированные количества отчётов и часов игры за весь доступный период. В запросе нет имени, города, Telegram ID, точных дат, полных ответов Google Форм или произвольного текста. При этом это всё равно данные о физическом и психологическом самочувствии человека, поэтому до включения требуется его осведомлённое согласие на обработку у внешнего провайдера OpenAI.

Настройки Railway:

- `OPENAI_API_KEY` — секрет из своего проекта на https://platform.openai.com/api-keys. Добавлять **только** в Variables Railway, никогда не отправлять в чат, Telegram и GitHub.
- `ZHUKOV_MONITOR_OPENAI_ENABLED=true` — включить только после согласия ученика и успешной тестовой проверки.
- `ZHUKOV_MONITOR_OPENAI_MODEL=gpt-4.1-mini` — модель по умолчанию, при необходимости изменить.
- `ZHUKOV_MONITOR_ENABLED=true` — существующий мониторинг остаётся активен независимо от настройки AI.

Используется Responses API с `store=false`, фиксированным JSON-форматом и тайм-аутом 20 секунд. При отказе модели, ошибке ответа или превышении тайм-аута основной отчёт остаётся прежним. Уже сохранённые исторические отчёты не перезаписываются и не отправляются повторно в API через `/zhukovreport`. В контуре опросов OpenAI ничего не записывает в исходные таблицы.

У OpenAI API отдельная от подписки ChatGPT тарификация; наличие ChatGPT Plus само по себе не оплачивает API. Ключ должен быть выпущен в отдельном API-проекте с контролируемым бюджетом и доступом к модели.

## 💳 Стоимость генерации в отчёте куратора

Когда AI-анализ OpenAI успешно завершён, в самом конце отчёта под предложением куратору отображается строка:

`💳 OpenAI API: ≈ $0.000690`

В Telegram значок 💳 остаётся emoji, а текст **OpenAI API** и сумма выделяются жирным через безопасную HTML-разметку Telegram. В служебном журнале сохраняется обычный текст без HTML-тегов, чтобы архив оставался читаемым. Заголовок, статус и названия разделов сводки также выделяются жирным в Telegram.

Сумма **рассчитывается для каждого конкретного вызова** по реальным `usage.input_tokens`, `usage.input_tokens_details.cached_tokens` и `usage.output_tokens` ответа Responses API. Используется тариф модели, вернувшейся в ответе, или запрошенной модели, если имя отсутствует; кэшированный ввод рассчитывается отдельно. Текущий стандартный тариф модели `gpt-4.1-mini`: вход $0.40, кэшированный вход $0.10, выход $1.60 за миллион токенов. Тарифы закреплены в `zhukov_ai.py` и требуют проверки при смене модели/цен: https://developers.openai.com/api/docs/pricing.

**Это оценка стоимости токенов, а не квитанция о фактическом списании.** Налоги, соглашения об оплате, лимиты, валютные конверсии и иные корректировки могут привести к отличиям от биллинга OpenAI. При отсутствии `usage`, неизвестном тарифе модели или нестандартном `service_tier` бот не выдумывает $0 — отображает, что стоимость рассчитать не удалось.

Расчёт применяется как к обычным новым AI-сводкам, так и к ручному `/zhukovai ДД.ММ.ГГГГ`. Повторный запуск ручной команды — **новый платный API-запрос**, а не запрос старого чека. Исторические отчёты не пересчитываются автоматически; при отказе API исходный отчёт не изменяется и фиктивная стоимость не добавляется.

## 🧪 Проверка OpenAI по уже заполненной анкете

В **личном чате куратора** можно вручную выполнить:

`/zhukovai 20.10.2026`

Команда читает настоящую утреннюю анкету за выбранную дату и предыдущие записи, строит компактную ретроспективную сводку без использования текущей фазы макроцикла, отправляет в OpenAI только обезличенные числовые/категориальные показатели и возвращает **новый** отчёт с AI-гипотезами только куратору. Поддерживается также `/zhukovai 2026-10-20`.

Проверка требует `OPENAI_API_KEY` и `ZHUKOV_MONITOR_OPENAI_ENABLED=true`, вызывает API и расходует оплачиваемые токены. При неправильном ключе, отсутствии средств, тайм-ауте или некорректном ответе бот прямо сообщает об ошибке, **не выдавая шаблон за AI**. Если за день нет утреннего отчёта, запрос не выполняется. Команда не изменяет Google Формы, служебный журнал, исторические сводки, контрольные сроки и не отправляет сообщение Алексею.

Команда является проверкой API и качественного анализа, но не заменяет автоматические отчёты будущих дней. Не запускать без осведомлённого согласия Алексея.

## 📚 История и просмотр отчётов по команде

В **личном чате куратора с существующим ботом Everest**:

- `/zhukovreport` — последний доступный день.
- `/zhukovreport 20.10.2026` — отчёт за выбранную дату (также принимается 2026-10-20).
- `/zhukovhistory` — последние 15 дат с анкетами, сохранёнными сводками или пропусками.
- `/zhukovhistory 30` — до 30 последних дат.

Если за дату есть подтверждённо отправленная сводка в журнале, команда возвращает **оригинальный сохранённый текст** с пометкой 💾 и добавляет решения куратора. Если сохранённой сводки нет, но есть утренняя анкета, бот вычисляет её анализ из имеющихся данных и маркирует 🔎 **ретроспективная реконструкция**. При реконструкции не переносит сегодняшнюю фазу макроцикла в прошлое. Если есть только постигровая анкета, выводит только подтверждённые факты. Если за дату отмечен пропуск, показывает запись о пропуске. Если данных нет — сообщает об отсутствии данных.

Команды **только читают** исходные Sheets и журнал, ничего не отправляют Алексею, не меняют историю и не используют OpenAI API. Доступны только авторизованному куратору **в личном чате с ботом**, не в группах. Длинные отчёты отправляются несколькими сообщениями без обрезки.

## Проверки

GitHub Actions выполняет компиляцию и тесты: расписание 30+24, дедупликация, поздние анкеты, границы времени, отдельная доставка куратору и Apps Script event mode.

Перед продуктивным включением дополнительно проверить безопасный ручной testAlexeyEventJournal (без внесения ответов в форму), права Editor, затем после **следующей подлинной отправки анкеты Алексеем** — живое событие Apps Script. Реальную доставку только в чат куратора, запись решения и отсутствие дублирования после перезапуска проверить отдельно. Последнюю проверку GitHub CI не заменяет.

**GitHub PR не устанавливает Apps Script триггер и не меняет Railway Variables.** Эти операции требуют авторизации в соответствующих сервисах.
